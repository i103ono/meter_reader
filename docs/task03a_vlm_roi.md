# 段階3追加：VLMによるROI提案

作業ブランチは `feature/image-agent-web`。段階4のPlannerを追加する前に、
ユーザーが承認した「GPTが領域を提案し、Pythonが検証・切り出し、Readerが独立して読む」方式を実装した。
仕様v0.2第1節では自動検出を後続としていたため、今回は明示的な追加範囲として扱う。
基準仕様書、旧CLI、取得済み画像・正解データは変更していない。

## 処理と確認手順

- `--auto-roi` は推論モードでのみ有効。同じ設定のOpenAIモデルをROI専用の別リクエストで使う。
- `--roi-only` を併用するとROI提案・切り出し・確認画像の保存だけを行い、測定値を読まない。
- `--roi-proposal <roi_proposal.json>` で保存した提案を再利用する。ROI用APIは再度呼ばない。
- 再利用時に `--roi X1 Y1 X2 Y2` または `--legacy-roi X Y W H` を指定して手動修正できる。
  元の提案座標・応答・過去runは保持し、新runに修正座標を保存する。
- 保存提案の質問・計器種別・観測IDをCLIが引き継ぐ。明示した別の質問／計器種別では再利用を拒否する。
  観測IDを引き継いでも実行IDは毎回別になる。
- 目視確認は枠・切り出し画像を見て行う。自動のROI承認、測定値の承認、Web上の確認操作は追加していない。
  手動座標指定も読取値の確認済み状態にはしない。

実行可能なコマンドは [README](../README.md#段階3追加gptによるroi提案と目視確認) に掲載した。
`--auto-roi --roi-only` で確認後、別コマンドの `--roi-proposal` で読取に進める。
一括実行では `--roi-only` を付けず、必要なら固定レシピを最大2つ指定する。
既定の `--mode mock` ではROI用もReader用も実APIを呼ばない。
保存済み提案の再利用と固定補正は、mockモード・APIキーなしで確認できる。

## 座標とモデルの役割

EXIF向き補正後の全体画像を、縦横比を維持して長辺1600画素以下へLanczos縮小する。
実際に送るPNG・画像サイズを保存し、GPTへその画像のピクセル座標で `[x1,y1,x2,y2)` を求める。
小さい画像は拡大しない。応答に値・単位・目盛値のフィールドを用意せず、領域提案だけを求める。

`located` / `ambiguous` / `not_found` を厳密なJSON Schemaとローカルの型検証で受け取る。
bool・float・文字列の座標、範囲外、空領域、項目不足、不整合な状態は拒否する。
曖昧さを示すissue codeと確定座標の矛盾も拒否する。無効な応答を修正依頼で再送しない。
対象が曖昧／存在しない場合、元画像全体へ戻して読み続けず、`needs_review` と理由を保存する。
API・構造不正は `error` として保存し、CLIは終了コード1を返す。

検証済み座標を、縦横それぞれの実倍率で元のEXIF補正後画像へ変換する。
左上は切捨て、右下は切上げとする。これは有効な座標の解像度変換であり、
不正座標を範囲内に切り詰める処理は行わない。元解像度で切り出すので、
GPTへ渡すための縮小画像をReaderの元ROIには使わない。

アナログは針先・全目盛・単位・倍率、デジタルは対象表示・単位・モード表示を含めるよう指示する。
質問文を保持し、複数計器／複数表示／二重目盛の対象が特定できない場合は提案を確定させない。
この指示でGPTの領域選択精度が保証されるわけではない。実応答を枠画像で確認する必要がある。

Readerへ渡すのは切り出し画像・計器種別・質問文だけで、ROI提案時の説明や推定値、
正解・evaluator・過去の値を渡さない。すべての固定補正は同じ未補正ROIから独立して生成する。
確認画像の枠や注釈をReaderの画像へ混ぜない。

## 記録と互換性

各runをUUIDで分離し、元画像・既存run・保存提案を上書きしない。
元画像のバイト列・SHA-256、EXIF補正後の画素ハッシュ、提案用画像のサイズとハッシュを記録する。
再利用時には入力ハッシュ・EXIF補正後画素・元サイズ・対象・座標変換の整合性を検証する。
ファイル名が同じ別画像には適用できず、同じバイト列のファイル名変更は許可する。

追加アセット：

| ファイル | 内容 |
|---|---|
| roi_locator_input.png | 今回GPTへ送った画像。保存提案の再利用時には作らない |
| roi_proposal.json | 提案の型付き記録。元の応答、モデル・プロンプト版、使用量・失敗を含む |
| roi_preview.png | 元解像度の確認画像。採用座標を緑、手動修正時は元の提案も橙で表示 |
| roi.png | 実際にReaderへ渡す未補正ROI。未解決のROIでは作らない |

`result.json` は既存フィールドを維持し、`roi_source`、`roi_proposal`、
`roi_proposal_reference`、`roi_preview_path`、`read_requested` を追加した。
`roi` は今回使った元画像座標、`roi_proposal.proposed_roi` は元の提案座標となる。
未解決の新しいROI処理では `source_image.roi_path=null`。この場合の `roi=null` は
`roi_source` と提案状態を合わせて確認し、全体画像を読んだ結果と混同しない。
従来の画像全体処理は `roi_source=full_image`、ROI画像は従来どおり存在する。

引数を追加しなければ従来の画像全体／手動ROI処理を維持する。既存の結果も新しい型で読み込める。
新規フィールドを一切許可しない独自JSON読み込み処理では、追加フィールドへの対応が必要になる。
ROI機能は段階4と区別し、`stage` は従来のReader／固定補正の段階番号を維持する。
`--roi-only` では `read_requested=false`、`reading=null`、最上位 `inference=null`。
ROIの通信記録は `roi_proposal.inference` に格納する。

## 予算

ROIとReaderは同じProviderを共有する。別Providerの組合せは拒否する。
`max_api_calls` は各論理リクエストの試行上限（最大2）、
`max_observation_api_calls` はROIを含む1画像の全送信上限（既定6、範囲1〜6）とする。
120秒以内の共有期限はROIの前から始め、Reader開始時にリセットしない。
通常はROI1＋未補正1＋補正2で4送信。429等の再試行も最大6送信へ含め、
残り枠がない候補は実行せず、理由と0送信を記録する。
設定済みの費用枠は同一CLIバッチ内で共有し、ROIも同じ予約・精算を使う。
料金設定がない場合の推定金額はnullのままにする。

保存提案の再利用では過去の通信記録を保存しつつ、今回の `api_calls` へ過去分を加算しない。
ROI確認と読取を分けた2コマンドは別runであり、同じ観測IDでも送信上限・期限・費用枠はそれぞれ適用する。
バッチ費用枠は別プロセスへ永続化しない。最上位 `inference` は引き続き未補正Readerの記録であり、
ROIや全候補を合わせた料金表示として使わない。各役割のtraceを参照する。
