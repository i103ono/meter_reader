# 追加範囲：対応点に基づく射影補正

作業ブランチは `feature/image-agent-web`。
仕様v0.2第3.3節で後続とした射影補正を、ユーザーの承認により単独レシピとして追加した。
基準仕様書を書き換えず、既存7レシピ・段階4・ROI機能を維持する。
Readerプロンプトの変更や、今回の画像を33等の値へ合わせる調整は行っていない。

## 構成と実行

- `perspective_rectify`：対応点と既知の平面形状からOpenCVの射影変換を行う。
- `--agent --allow-perspective`：Plannerへ新レシピを提示し、選択時に専用VLM要求で対応点を確認する。
- `--perspective-config <JSON>`：単一ROIの手動対応点。agentの選択肢を有効にし、対応点用APIを省略する。
- `--recipes perspective_rectify`：手動対応点が必須。MockReaderでAPIなしに画像処理を確認できる。
- `examples/demo_perspective.py`：既知の平面四隅を持つ人工画像と設定を生成する。

実行可能なコマンドとJSON形式は [README](../README.md#追加レシピ対応点を用いた傾き補正) に記載した。
既定のagentには新レシピを提示しない。明示的な有効化なしに追加のVLM通信を行わず、
無効時はPlannerのレシピ一覧・出力Schemaからも外す。実行境界でも拒否する。
既存のパラメータ不要7レシピは `tools.RECIPES`、全8レシピは `tools.REGISTERED_RECIPES` で管理する。

## 幾何の契約

対応点はEXIF補正・切り出し後の元ROI内の画素中心座標である。
右下を含まない元画像ROI範囲指定と混同せず、点には `0 <= x <= 幅-1`、`0 <= y <= 高さ-1` を要求する。

手動設定は以下のいずれか。

| reference | 点順 | 既知の形状 |
|---|---|---|
| rectangle | 左上、右上、右下、左下 | aspect_ratioで実物の幅÷高さを指定（0.25〜4） |
| dial_cardinals | 物理的な円の上、右、下、左 | 円。aspect_ratioはnull |

自動提案は、向きの根拠がある円形アナログ文字盤の物理的な四点だけを対象とする。
見かけの楕円の上下左右、円を囲う仮想四角、立体ケースの縁から点を作らせない。
隠れている点・向きが不明な点を補わず、`ambiguous`／`not_found` として停止する。
既知の向きの根拠がなければ楕円だけから正しい正面像は一意に決まらないためである。
自動要求はROIを再縮小せず、その画像の座標で返す。各辺2048画素を超えるROIや、
明示的なdigital指定ではAPIを使わず曖昧として手動設定を促す。
矩形計器の未知の実物縦横比をVLMへ推測させない。

Pythonは厳密な型・有限性・範囲・時計回りの凸四角形・辺長8画素以上・面積1%以上を検証する。
最小ROIは32×32。逆順・重複・交差・退化した点は修復しない。
単位サイズ座標での行列条件数100以下を要求し、特異行列と過度に不安定な変換を拒否する。
逆変換で出力四隅が元ROI内にあり、射影の無限遠線をまたがないことを確認する。
元ROI外の未知の画素を必要とする補正を実行しない。

出力は、円なら正方形、矩形なら既知の縦横比に基づく矩形。
長辺は `min(元ROI長辺, 2048)`、画素上限6400万を適用し、実際のサイズを記録する。
対応点から `cv2.getPerspectiveTransform` で行列を計算し、`INTER_LINEAR` で再標本化する。
RGBAはpremultiplied alphaで補間する。明るさ処理や拡大との合成レシピは追加していない。

## 保存・再生成と予算

候補の処理版は `perspective-v1`。元の7レシピの `fixed-recipes-v1` は変更しない。
`geometry` に元ROIハッシュ、手動／VLM／mockの出典、対応点、根拠、状態、応答・通信記録を保存する。
`steps` に出力先対応点、変換行列、出力サイズ、補間・alpha処理・上限を記録する。
生成時には `candidates/cN_perspective_points.png` を確認用に保存し、Readerへ注釈を渡さない。

候補は常に元ROIから独立して生成し、元画像・ROI・既存runを上書きしない。
Readerへ渡すのはその画像・質問・対象種別だけで、対応点の説明・正解・履歴を渡さない。
幾何専用要求にも測定値・正解・前日値を渡さず、測定値を返せるフィールドを設けない。

オフライン再生成では対応点と行列の整合性を検証後、**保存済み行列**で再生成する。
行列・条件数の照合はライブラリの丸め差を1e-10で許容し、それ以外のパラメータは同一性を要求する。
ROIハッシュの不一致、改変した行列／対応点／処理版を拒否する。
VLMによる点の再推定はしない。画素・PNGハッシュの一致と実行環境の差は別に報告する。

対応点APIもReader・Planner・ROI提案・最終比較と同じProviderの最大6送信・120秒・料金枠を使う。
対応点確認が最後の枠を使った場合は画像変換・読取をせず、対応点記録と未実施理由を保存する。
`candidates[].api_calls` は幾何とReaderの合計、`geometry.api_calls` は幾何のみ、
`candidate.inference` は従来どおりReaderの記録となる。最上位で二重計上しない。
手動指定の幾何通信は0回で、mockで物理対応点を自動作成しない。

曖昧／不在は `geometry_ambiguous`／`geometry_not_found` として要確認・CLI終了コード0。
不正な数値・構造・通信障害は技術エラーとして記録し、CLI終了コード1となる。
未生成画像をReaderへ渡さず、候補数上限2を維持する。
座標の形式・数値が正しくても、物理的に正しい対応点かは人の確認が必要である。
`auto_accept=false`、採用値nullを維持し、今回の画像で精度が改善したとは扱わない。

## 検証結果

`uv run --locked --offline python -m unittest discover -s tests -v` で、
既存140件＋新規24件＝164件が成功した。

- 既知の四隅で人工的に射影した画像を補正し、色付き特徴点の位置・色が戻ることを確認。
- 恒等変換、円の物理四点、RGBAの色・alpha、EXIF補正後のROI内座標を確認。
- 不正型、NaN、点順・重複・退化・小領域・範囲外・過度な変形・出力上限を拒否。
- 手動・自動・無効化、曖昧／不在時の停止、デジタルの未知縦横比の拒否を確認。
- 幾何の通信再試行・最後の送信枠・期限・料金枠を共通予算で検証。
- Reader／幾何入力へ正解・前日値が混入しないことを確認。
- 保存行列の改変を拒否し、APIなしで再生成して画素・PNGハッシュが一致。

人工デモを実行し、傾いた図形から円と特徴点が戻った補正画像を目視確認した。
実画像20枚（圧力計10、電力量計6、流量計1、パルスオキシメーター1、電子ノギス2）でも、
任意の画像四隅を用いた接続確認用設定で画像入力・保存・20補正画像の再生成を確認した。
この設定は実物の文字盤平面の正解対応点ではなく、幾何精度評価には使用しない。
別の20runでは模擬Plannerと模擬の曖昧な幾何応答で、変換・Readerを実行しない停止を確認した。

模擬HTTP60送信、実API0、外部ソケット0。
元画像20枚、入力、labels.jsonl／labels.csv、provenance、再生成元runは不変。
記録は `outputs/perspective-verified-y73k0lx5/validation_summary.json`。
入力・正解・出力はGit管理外である。

実VLMの対応点選択、今回のタイヤ圧力計で補正できるか、読取精度・処理時間・実費は未検証。
ユーザーの方針に従い、クラウドで実APIは使わない。
確認済みROIを再利用してローカルで `--agent --allow-perspective` を実行し、
選択レシピ・geometryの状態・点の確認画像・補正画像・候補の読取を確認する必要がある。
