# 段階5：比較評価と履歴の永続保存

作業ブランチは `feature/image-agent-web`。
仕様v0.2第7節、第9節の段階5、第12.3節の保存区分を実装した。
読取精度の調整はユーザーの指定により後続へ残し、Reader・Plannerの読取／補正判断を変更していない。
クラウドでは実APIを呼んでいない。

## 既存コードからの流用と分離

画像入力・EXIF・ROI、固定補正、独立Reader、最大2候補のagent、通信予算、保存runを流用した。
既存 `evaluate.py` は旧CSV形式（status=ok、単一正解値等）の評価CLIとして維持する。
新しい `evaluation.py` はv0.2の欠損・棄権・状態と元データの区間正解を扱う別処理とした。
正解の形式に合わせてモデル出力を直したり、Reader／Plannerへ正解を渡したりしない。

## 履歴

`repository.py` は標準ライブラリsqlite3とDB所有の画像コピーを使う。
初期スキーマ版は1。不明な版のDBを上書きしない。

| テーブル | 保存するもの |
|---|---|
| meters | 固定meter_id、現在の表示情報・登録情報・系列版 |
| meter_versions | 各系列版の登録情報のスナップショット |
| observations | 観測ID、meter_id・系列版、撮影日時・根拠・タイムゾーン、ハッシュ、初回ROI、選択中run |
| read_runs | 元の予測JSON、ハッシュ、処理日時・モード・読取状態 |
| reviews | run単位の確認・訂正・却下、理由・確認者・時刻。追記のみ |
| assets | 画像ID、run内の名前、DB管理コピーの相対パス・ハッシュ・サイズ |
| run_selections | 選択run変更の履歴 |

保存はUTC、元の撮影タイムゾーンと根拠は保持する。不明な撮影日時はnullのままで、現在時刻を代入しない。
単発CLIのmeter_id省略は許可する。明示されたIDだけを関連付け、名前や画像から同じ計器と推測しない。
IDだけ指定した未登録計器は、単位・目盛不明の最小登録を作る。登録単位・目盛等の変更には新しい系列版を要求する。
過去の系列版を別の測定条件へ使い直せず、古い観測には当時の登録情報を保持する。

同じobservation_idの再読取は別runを追加する。
画像ハッシュ・meter_id・撮影日時の矛盾は拒否し、同じIDで別観測へ置換しない。
再読取でROIを変更することは許可し、初回ROIと選択runのROIを区別する。
撮影日時や計器との関連を後から書き換える操作は今回追加していない。

元の予測JSONは変更せず保存し、SQLiteのtriggerでもrunとreviewのUPDATE／DELETEを拒否する。
人の確認はknownな既存候補を指定する。訂正は有限の十進数値・単位を明示し、0もそのまま保持する。
目盛の訂正はsource=manual、登録値はsource=registryで、画像抽出のimageと区別する。
確認状態と採用表示値は選択runの最後のreviewから計算する。別runへ選択を変えると、以前の確認は無条件には移らない。
元のread_statusは保持する。確認済み表示値をモデルの自動採用結果successへ変えない。

runの再取込は同じ内容なら冪等、異なる内容ならエラー。
review_idを明示した確認要求も同じ内容だけ冪等とする。
SQLトランザクション中のファイル保存失敗はDBをロールバックし、その取込が作ったコピーを削除する。
元run・元画像を削除しない。プロセス強制終了時に未参照のコピーが残る可能性はあるが、未コミットrunを履歴へ表示しない。

コピー対象はresult.jsonから参照される画像と既知の付随ファイルに限定する。
元画像パスの絶対パスからコピーせず、run内の相対参照を使う。パス逸脱・symlink逸脱・欠損・ハッシュ不一致を拒否する。
DB内部の保存先は入力IDに依存しないUUIDディレクトリで、API用の参照には画像IDを使える。
get_assetは読込時にもハッシュを確認する。DBと隣の `<DB名>_assets` を一緒に保持する。

既存CLIは `--database` を指定した場合だけDBへ取込む。
新runを通常取込すると選択runを更新する。`import --keep-selected` や比較実験の取込では既存選択を維持する。
DB保存が失敗しても、既に保存した元runのパスはstdoutへ残り、CLIは非0で終了する。
表示・取込・選択・reviewのCLIを `history_cli.py` に追加した。Web操作は段階6で同じRepositoryを利用する。

## 比較実行とラベル分離

`benchmark.py` は入力専用のObservationInputだけを受け取り、ラベル引数・ラベル読込を持たない。
全ケースを事前検証し、全A〜Dの予定行をmanifestへ宣言してから実行する。
欠損・API障害・保存失敗等も行を削除せず残し、同じ共通N件で集計する。

- A：全体画像。EXIF補正は全条件で共通。
- B：未補正ROI。
- C：実行前に指定した7固定レシピのうち1つ。その補正候補c1を評価する。
- D：既存agent。選択された表示候補のみを評価し、選択なしは棄権。

B〜Dは同じ座標・質問・対象種別を使う。ROIは事前の手動指定／保存提案で確定し、比較中にROI用APIを呼ばない。
単一画像は `--question-id`、JSONLは `dataset.question_id` でラベルへ対応付ける。
既定ではROIを必須とする。`--allow-full-image-roi` は全体画像ROIの接続確認用であり、切り出しの効果を示さない。
Cの既定gamma_mildは実行例で、評価から選んだ最良レシピとはしていない。
射影補正は `--allow-perspective` でDへ追加できるが、パラメータ付きの射影補正をCへ暗黙に選ばない。

同じモデル・Readerプロンプト・画像detail・最大出力を検証する。
各runの6通信・120秒上限は維持し、料金枠を設定した場合はCLI全実行で共有する。
実験のAPI回数は1枚の単発agentより増える。比較用に予算上限を緩める処理は追加しない。
実行結果はUUIDで分離し、予測・manifestのハッシュを記録する。ラベルでレシピや候補を選び直さない。

## 評価

`evaluation.py` は保存済みmanifest／resultとlabels.jsonlまたはlabels.csvだけを読む。
画像読取、API呼出し、モデルの再実行、人の訂正値の利用を行わない。
入力ハッシュ・question_id・ROI・質問・設定・宣言レシピ・事前指定候補を照合し、不一致を拒否する。

取得済み20件は `interval_matching` 15件と `multi_interval_matching` 5件だった。
後者は単位群と区間の対応を保持し、例えばbar用の値をpsiの区間へ照合しない。
複数区間で単位を特定できない場合は数値を別の単位の区間に照合しない。
単一区間では値の正解と単位の正解を独立に判定する。
元evaluator／kwargs／区間・単位候補・出典をレポートへ保持し、中央値に書き換えない。

アダプター名はlocal-closed-interval-v1で、公式evaluatorのコード実行・完全互換検証はしていない。
閉区間・明示した単位候補の照合を実装し、未対応のevaluator／kwargsは黙って近似せず拒否する。
単位の別名は明示表だけで扱い、Pa↔MPaやmW↔MWを文字列正規化で同一にしない。
十進数で照合し、単一値の符号・小数点を確認する。末尾0等の元表記も残る。

共通N件で値・単位・総合正解率、棄権・状態別率・技術エラー率を出力する。
needs_reviewの抽出候補成績と、自動採用率・自動採用結果の誤り率は別の項目にする。
自動採用0件の誤り率はnull。区間の数値誤差は対応する区間までの距離とし、区間の中央を基準にしない。
単位不一致時は数値誤差を計算せず、区間正解や正解0の場合の相対誤差も未定義のままにする。

時間・API回数・トークン・金額は全役割を集計する。Readerのbaseline traceを候補と二重計上しない。
保存提案の過去のROI通信も今回の費用に加算しない。通信失敗で使用量が不明なら合計もnull。
料金設定がない場合に0円とは表示しない。
Mockはaccuracy_evaluated=false、数値の正解率はnullとし、配線検証を精度として報告しない。

## 検証結果

`uv run --locked --offline python -m unittest discover -s tests -v` で、既存164件＋新規40件＝204件が成功した。
DBの再起動・元run削除後の参照、画像ハッシュ、取込／reviewの冪等性、ロールバック、
系列版・撮影日時、候補確認・0の訂正・手動目盛・却下・確認状態の分離を検証した。
評価は区間端点、単位別複数区間、十進数・符号・単位倍率、共通分母、棄権、固定候補、
改変・設定不一致、ラベル形式、Mock精度抑止、CLI・別プロセス読込を確認した。
数値を使うテストは人工のラベルと架空HTTP応答であり、実画像の性能評価ではない。
旧evaluate.pyの--helpも起動確認した。旧形式のdata/evaluation_labels.csvは未配置のため、旧CLIによる精度評価は未実施。

公開開発画像20枚でA〜Dの80runをMockReaderで保存し、SQLiteへ20観測・80実行・380アセットを取込んだ。
DBを開き直して全画像・JSONのハッシュを確認し、別プロセスのCLIでも同じ観測の4実行を参照できた。
labels.jsonl／labels.csvの評価集計が一致し、元画像・ラベル・入力・provenanceは不変だった。
全体画像ROIの接続確認モードを明示し、正解率やROIの効果は評価していない。
全観測はunreviewed、採用表示値はnullのまま。実API0回・外部ソケット0回。

記録は `outputs/stage5-verified-oapfdamp/validation_summary.json`、
実験manifestとDB・評価レポートも同ディレクトリ以下にある。
今回添付された最新result.jsonは新しい型で検証できたが、添付ディレクトリに画像一式がないため
その実runのクラウドDB取込は未実施。ローカルの元runディレクトリはREADMEのコマンドで取込める。

実APIでのA〜D、数値の正解率、人工劣化／実環境での改善効果、公式evaluatorとの完全互換性は未検証。
公開20枚は開発・接続確認用のままで、企業画像の最終性能評価には使用しない。
段階6のWeb、段階7の前日比較・CSV／Excel出力は追加していない。
